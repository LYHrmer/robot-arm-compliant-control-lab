# 逐拍读懂负载调度与轨迹验收

补偿预算降到 6 N 后，下一拍输出一定不能超过 6 N 吗？在本项目中，输出还要遵守
20 N/s 的变化率限制。两条约束作用的位置不同。

先读 [Franka 数值解算](03_franka_numerics.md)中的 wrench 到关节力矩，再看
[在线补偿](../online_compensation.md)的系数更新。这里只讨论在线补偿外层的 6–8 N
预算调度；BC/PPO 不参与这条控制路径。

## 用一拍把变量分清

控制周期为 $\Delta t=0.002\ \mathrm{s}$。设本拍预算为 $b_k$、等效负载系数为
$\mu_k$、修正后的法向力为 $F_{n,k}$、接触混合权重为 $\beta_k$。切向目标速度
$v_{t,k}$ 用来构造平滑方向：

$$
d_k=\frac{v_{t,k}}{\sqrt{\|v_{t,k}\|^2+0.005^2}},\qquad
f_k^*=\beta_k\min(\mu_k F_{n,k},b_k)d_k.
$$

$d_k$ 的长度小于 1。图上的力小于预算，也可能已经触发内部幅值限制。
接着用上一拍请求 $f_{k-1}$ 限制本拍变化：

$$
f_k=f_{k-1}+(f_k^*-f_{k-1})
\min\left(1,\frac{20\Delta t}{\max(\|f_k^*-f_{k-1}\|,10^{-12})}\right).
$$

若上一拍为 7.70 N，缺包使预算立即回到 6 N，本拍沿原方向最多下降 0.04 N，
可以仍有 7.66 N。这里满足全局 8 N 硬上限和变化率约束。把输出突然裁到 6 N，
反而改变了既定控制器。接触丢失另有清零分支，不在连续变化率保证内。

计算在 [`TangentialCompensation._online_force`](../../src/compliant_control_lab/tangential_compensation.py)。
外层 [`LoadAwareCompensation.force`](../../tools/load_aware_compensation.py)只在父类计算期间
提供本拍预算，计算后恢复全局上限。

## 沿时间顺序看状态

| 时刻 | 本拍读什么 | 留给下一拍什么 |
|---|---|---|
| 接收辅助力包 | 力向量、时间戳、是否存在 | 只接受有限、未过期且未乱序的包 |
| 计算补偿请求 | 旧系数 $\mu_k$、本拍预算 $b_k$、测得运动状态 | 限速后的请求和运动确认状态 |
| 关节力矩投影 | 当前完整 wrench 与力矩余量 | 本拍请求能否原样执行 |
| 更新系数 | 测得运动误差、当前预算、投影结果 | $\mu_{k+1}$，上限处禁止正向累积 |
| 更新预算 | 有效辅助力、运动方向、同一投影结果 | 滤波负载 $L_{k+1}$ 和预算 $b_{k+1}$ |

预算用单位速度方向投影测得负载，再以 0.20 s 常数低通，增加 0.25 N 余量并限制在
6–8 N。公式见[负载调度](../load_budget.md#一拍内的顺序)。滤波只在允许更新的拍数上推进，
停止期间不应把 0.20 s 当成墙钟响应时间。

缺包或拒收辅助力包时，预算和负载估计回到最小配置，原系数保留，仍按运动误差和原门控更新。
停止、换向、请求限速、接触混合尚未完成会影响运动确认；力矩投影另外决定能否提交更新。

## 测量记录到什么程度才够

| 记录层次 | 字段示例 | 用途 |
|---|---|---|
| 注入误差前的原测量 | `measured_wrench_world` | 核对原法向反馈，追溯辅助包来源 |
| 故障后的原始辅助包 | `raw_load_packet_force`、`raw_load_packet_stamp`、`raw_load_packet_present` | 重建实际故障输入 |
| 送给调度器的输入 | `load_force_local`、`load_measurement_available`、`load_packet_status` | 检查拒收后是否复用旧力 |

包龄上限为 20 ms。重复时间戳在未过期且不早于上一次接受的时间戳时允许使用；丢失、非有限、
未来、过期或乱序包不送入调度器。被拒收行的送入力和时间字段写零，同时标记不可用。
这些零是占位值，不能解释成测到了零负载。

故障只作用于辅助负载通道。原法向控制反馈没有被同时切断，所以这不证明整个六维力传感器
失效时仍能控力。实际机械臂没有 F/T 传感器时，还需另行解决力估计和标定。

## 先跑数值测试，再读闭环结果

安装依赖后在仓库根目录运行：

```bash
pytest tests/test_measured_budget_validation.py tests/test_measured_budget_trial.py -q
```

[`controller_trace`](../../tests/test_measured_budget_validation.py)从控制器重置状态开始记录
完整序列，特意用较高目标速度触发下降预算的边界。它是状态机测试，不是机械臂性能曲线。
`test_historical_validator_rejects_the_legal_transient` 保留旧验收误判的复现。

独立验收入口 [`validate_trace`](../../tools/measured_budget_validation.py)从记录的输入逐拍
重算状态，不调用控制器生成期望答案。缺少 `measured_position` 或 `measured_linear_velocity`
就拒绝完整回放；不能用真实状态补齐。原 60 条精简轨迹仍保留
`coefficient_transition_checked=false`，新测试不会替它们补上没有记录的证据。

动手时每次只改测试副本，不修改已发布归档：

1. 在缺包序列中定位第一拍预算回退。检查请求变化不超过 0.04 N，并算出回到 6 N 以下
   用了多少拍。再解释为什么系数没有随辅助测量一起清零。
2. 把一拍的 `controller_coefficient_after_compute` 加上 `1e-4`，确认独立验收报错。
   只检查输出有没有超过 8 N，为什么发现不了这类错误？
3. 把目标速度反向，找到运动确认重新成立的那一拍，再核对预算第一次更新的时刻。
   限速与 50 ms 运动确认分别推迟了哪个步骤？
4. 对同一闭环工况比较固定 6 N、固定 8 N 和调度预算，同时列出位置与速度误差，再检查
   原有接触力门槛。不能只选择其中一条更好看的曲线。

后续读 [C++ 控制核心](../cpp_core.md)时，先找这些状态的对应实现，再运行 parity。
移植成功的依据是同一输入历史下的逐拍一致性，编译通过只完成了第一步。
